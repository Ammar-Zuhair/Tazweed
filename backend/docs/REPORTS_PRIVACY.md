# تنفيذ11 — التقرير الشهري والخصوصية وحذف الحساب

هذه خدمات فعلية في Express/PostgreSQL، وليست mocks. [الخطة](phases/11.md) و[تقرير التحقق](progress/phase-11.md). لا تنفيذ12 ولا نشر خارجي. فحص OTP/R2/Routing/Push الحقيقي والهاتف مؤجل بطلب المالك.

## التقرير الشهري

POST `/api/v1/admin/reports/monthly-sales` يستقبل year/month/branchIds صريحة مع Idempotency-Key. يحتاج reports.read لكل فرع قبل الرد المحفوظ وداخل المعاملة. لا افتراض لجميع الفروع من قائمة فارغة. ستة طلبات/ساعة لكل موظف؛ يعيد ID لمهمة pending. العامل يأخذ مهمة بقفل SKIP LOCKED وsnapshot REPEATABLE READ، ويتحقق من المستخدم والجلسة والصلاحية الحالية. فشل SQL/Chromium ينتج failed برسالة آمنة، ولا PDF وهمي أو تفاصيل stack. إنشاء جديد بعد الفشل بمفتاح جديد. المحاولات المعلقة تعيد المفتاح والمحتوى نفسيهما.

GET `/admin/reports/:id` و`/:id/download` يحتاجان صاحب المهمة وصلاحية كل فروعها حيًا؛ لا وصول عام أو رابط R2 أو إيصالات أو هويات عملاء في PDF. الملف bytea خاص في DB، ومتاح يومًا واحدًا كذاكرة تقنية مؤقتة ثم تزيل الخدمة البايتات والملخص؛ ليس ذلك مدة احتفاظ محاسبية. يلزم Chromium المثبت بـsetup.sh. الخط Tajawal محلي مضمن، والعربية يشكلها محرك Chromium. لا تحميل خطوط/صور أو تشغيل JavaScript من بيانات التقرير.

`REPORT_TIME_ZONE` يحدد حد الشهر المحلي، مع تخزين timestamps UTC ونطاق نصف مفتوح `[start,end)`. القيمة الحالية UTC موسومة للمعاينة، وليست اعتماد D15. اختبر UTC وAsia/Aden وحدود الشهر. PDF يذكر المنطقة وبداية ونهاية الفترة وتاريخ snapshot. تعديل الفروع/الفترة في الشاشة لا يغير ملفًا سابقًا؛ اسم تنزيله من فترة snapshot.

المبيعات = آخر عرض ثابت للطلبات **المسلّمة داخل الشهر** فقط. المؤكد غير المسلم والملغي والمرفوض ليسوا مبيعات. يعرض عدد الطلبات المسلمة، وقيمة المنتجات وخصمها، وأصل التوصيل وخصمه ورسوم العميل وإجمالي المسلّم. لا يعرض أعداد المخزون أو raw counts لقاعدة البيانات.

حركات الأموال مستقلة حسب تاريخها وقد تخص طلبًا من شهر آخر: التحويل المتحقق منه من سجل المراجعة، والتحصيل النقدي الفعلي وتصحيحاته، والتوريد وعكسه وصافيه، وعمولة التسليم وتصحيحاتها، والصرف وعكسه وصافيه، والاستلام/الرد/الشطب/other الخارجي كل على حدة. لا تعتبر الوعود أو الصورة مالًا، ولا تجمع الحركات مع المبيعات. مصادر تخصيص الصرف/التوريد توزع كل حركة على فرع الطلب الأصلي، بما في ذلك سلسلة reversal credit وإعادة تخصيصه؛ لا تضاعف header لكل item، ولا يعد credit عمولة مكتسبة. المال decimal strings وBigInt عند التجميع، لا floating point أو مقاصة تلقائية.

الإدارة تنزل PDF بطلب Bearer حي. الويب ينزل Blob مؤقتًا، وAndroid/iOS يكتبان ملف cache مع expo-file-system ثم expo-sharing ويحذفانه بعد إغلاق المشاركة؛ لا نشر لرابط خاص. نجاح الويب والحزم لا يثبت حفظًا/مشاركة على هاتف فعلي.

## الحذف والتحقق والمتابعة

Express يخدم `/privacy /terms /support /delete-account` وملفات CSS/JS/Tajawal محلية. لا تطبيق ويب خامس ولا حاجة لتثبيت التطبيق أو تسجيل الدخول لتقديم الحذف. صفحة Express تستخدم JSON وX-Deletion-Flow ولا cookies؛ رفض cross-origin عبر CORS ورفض الطلب بدون header، فلا يوجد اعتماد على جلسة cookie. محتوى المالك escaped، ورسائل المتصفح textContent، وHelmet/CSP بلا inline scripts.

الويب: POST `/web/account-deletion/start` ثم `/verify` ثم `/status`. التطبيق: `/api/v1/me/deletion-requests/start` بجلسة ونوع مطابقين، ثم `/api/v1/account-deletion/verify` ببرهان preauth مستقل، و`/account-deletion/status` بمفتاح المتابعة. يبقى POST `/me/deletion-requests` وGET المملوك `/:id` متاحين بالعقد الموثق. صلاحية proof خمس دقائق وخمس محاولات، send60 ثانية، وحدود مشتركة DB للهاتف/IP/device. لا تسجيل لكود أو preauth أو مفتاح المتابعة أو الهاتف. unknown phone له شكل start نفسه؛ لا يثبت وجود حساب قبل امتلاك الرمز.

challenge مقيد delete_account/app/phone/device/preauth/generation؛ لا يفتح جلسة ولا يقبل رمز login/reset. تتثبت source app/web في payload المشفر عند البدء، ولا يختارها العميل في verify. التحقق ينشئ طلبًا واحدًا، ويستهلك جميع تحديات الحساب، ويبطل جميع sessions وPush ويضع deletion_requested_at ذريًا. يصطف submit مع قفل users نفسه ويرفض الجديد بعد الطلب؛ يبقى تسجيل دخول جديد لمتابعة الجاري ممكنًا حتى إزالة الحساب. لا تسجيل Push جديد لحساب طلب حذفه. طلب مفتوح لا يرفض استقبال الحذف، ولا يلغي الطلب أو يحرر حجز receipt_review تلقائيًا.

رقم المتابعة UUID ومفتاح HMAC سري يقرؤان الحالة فقط؛ لا عنوان أو هاتف أو أموال في DTO. لا توضع الأسرار في URL. يحفظ التطبيق قدرة المتابعة في SecureStore، والويب في sessionStorage، دون حفظ OTP أو preauth. يحفظ مفتاح المتابعة **قبل** verify ليمكن الاستعلام بعد فقد ACK حتى إذا حذفت الهوية. replay البرهان نفسه يعيد الطلب، ولا يكرر الحذف. يمكن لرقم حساب باقٍ للمراجعة استرجاع المتابعة برمز جديد، وتدوير المفتاح؛ challengeId الجديد يعمل كalias للرقم القديم. بعد اكتمال إزالة الهاتف، يلزم مفتاح المتابعة المحفوظ.

## التعمية والصلاحيات والحدود

0008 إضافية؛0001–0007 ومخطط reference69 دون تعديل. دور tazweed_privacy باقٍ NOLOGIN، بلا عضوية HTTP أو DDL أو UPDATE/DELETE لدفتر المال. المهاجر يحتاج عضوية privacy لنقل ملكية الدوال؛ لا تمنحها للتطبيق. CREATE مؤقتة تنزع بعد نقل الملكية. الدوال SECURITY DEFINER بأسماء جداول مؤهلة وsearch_path ثابت، ولا تقبل SQL أو اسم جدول من HTTP. gates التحقق والسياسة والالتزامات داخل القدرة نفسها. لا منح UPDATE لنسخ الأسعار أو revision أو المخزون.

بعد سياسة معتمدة وفحص الالتزامات: حذف الاسم والهاتف/hash والعناوين والجلسات/refresh وOTP وPush/inbox ومحتوى التقييم/الشكوى/البلاغ، مع إبقاء مستخدم tombstone UUID لسلامة FK. لا حذف متسلسل لدفاتر الطلب/المال. آخر مدير عام أو رصيد نقد/عمولة موصل أو طلب/دفع/استثناء/حجز/شكوى جارٍ يبقي needs_review. المرفق المشترك مع حساب آخر يحتاج فصلًا ومراجعة قبل إزالة الهوية. أصل البلاغ المالي ونسخ المال/audit لا يفتحان للتعديل.

عنوان/تواصل order_private_details يعميان بحارس SQL أحادي الاتجاه بعد نهاية الالتزامات ومدة personalDays من أحدث إنشاء/تسليم/event للطلب؛ ملفات الإيصال/proof الخاصة من الأحدث بين إنشاء الملف وإزالة الحساب +transactionDays. غير اللازمة تدرج للحذف دون مدة قانونية افتراضية، مع انتظار انتهاء PUT الموقع إن ظل صالحًا. تدرج أيضًا مرفقات البلاغات/الشكاوى الخاصة التي رفعها موظف عن العميل. لا تزال الصور العامة للكتالوج المملوكة للمتجر عند حذف موظفها.

عامل R2 يحذف original/staging/thumbnail ثم يعلّم deleted؛ الفشل يعيد المحاولة ولا يعلن completed. يبقي أي إثبات مرتبط بطلب/استثناء جارٍ، حتى لو حذف حساب رافعه. لا completed مع snapshots أو ملفات في الطابور. بيانات مالية دنيا وسجل audit بمعرفات مقيدة تبقى موثقة في notice؛ **لا ادعاء anonymization لكل نص حر ولا حذف دفتر مالي**. تدقيق احتواء الملاحظات المالية/الإثباتات على بيانات شخصية وسياسة مراجعتها القانونية من المالك شرط إطلاق، لا مدة قانونية مفترضة من المطور.

عند اكتمال إعداد سياسة أمنية معتمدة، ينظف العامل تحديات OTP المنتهية بعد securityDays وعدادات rate المنتهية؛ لا يحذف تحديًا صالحًا ولا audit. إبطال session فوري عند التحقق، ثم إزالة سجلاتها عند التنفيذ. رابط GET خاص صدر قبل الحذف قد يبقى صالحًا حتى90 ثانية ما لم يزل object، ولا يمكن سحب بايتات سبق تنزيلها.

العمليات الإدارية GET `/admin/deletion-requests` وPOST `/:id/process` تحتاج privacy.manage عامة، وتفويضًا حيًا داخل المعاملة؛ لا override للسياسة أو الأرصدة. العامل يستأنف طلبًا كل دورة، ويوقف claims عند SIGTERM وينتظر ما بدأه. إعداد سياسة كانت ناقصة يثبت snapshot في أول محاولة بعد اكتمال القيم؛ النسخة المعتمدة لطلب قائم لا تتبدل بصمت.

## ما يمنع قبول السياسة والإطلاق الآن

اسم الجهة ووسائل الدعم والنسخة/تاريخ الاعتماد ومدد personal/transaction/security/backup/target غير مقدمة من المالك. تقرأ الصفحات الإعدادات الفعلية، وتظهر مسودة واضحة دون مدد مختلقة؛ privacy=unconfigured وready503، وproduction يرفض البدء بسياسة ناقصة. التحقق يستقبل الطلب ويبطل الجلسات ثم يحتاج مراجعة السياسة، ولا يعد بحذف مكتمل. كذلك لا توجد سياسة نسخ أو purge قانوني للدفاتر ولا مزود OTP محدد بعقد محو سجلاته؛ متطلبات مزودي البيانات والنسخ قبل الإطلاق باقية وفق D19/D20 والجولة المؤجلة. كتابة أرقام في اختبارات معزولة لا تعني اعتمادها للمتجر.
